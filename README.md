# 幻梦 P2P (phantom-p2p)

**虚拟局域网组网工具** —— 让分布在不同网络下的设备像接在同一台交换机上一样互通。

用 Rust + Tauri 实现，客户端与服务端全部可自建、全部开源。核心是一套完整的 NAT 穿透引擎：
探测双方 NAT 类型 → 按 NAT 配对选择打洞策略 → 打洞失败才回退到中继。

## 它解决什么问题

你有两台设备分别在两个不同的家庭宽带 / 校园网 / 蜂窝网络下，想让它们直接互访（联机、远程桌面、内网服务）。
公网 IP 没有、端口转发做不了、NAT 挡在中间。

幻梦 P2P 的做法：

1. 一台设备开房间当 **Host**，其他设备加入当 **Guest**；
2. 双方通过信令服务器交换 NAT 画像与候选地址；
3. 服务端按双方 NAT 类型下发**打洞策略与角色分工**，双方在统一时刻发起打洞；
4. 打洞成功 → 建立 **P2P 直连**；打洞失败 → 回退到**中继**；
5. 双方各自创建一张虚拟网卡（TUN），三层流量在隧道里透明转发。

## 3.0.0 更新说明（重点）

> 3.0 是一次**结构性重写**，不是版本号跳跃。协议、打洞引擎、数据面、服务端端口模型全部改了。

### 为什么要做这次重写

2.x 的实际表现是：**打洞成功率低到几乎所有房间都退化成中继，中继带宽被打爆**。
排查之后确认这不是调参能解决的问题，根因有三条，全部在架构层面：

#### 1. 候选在知道对端 NAT 类型之前就生成了

2.x 的流程是"先各自生成候选 → 再交换 → 再打洞"。
这意味着**在候选生成的那一刻，客户端根本不知道对端是什么 NAT**。
于是所谓"按 NAT 组合选策略"从架构上就不可能实现——策略需要的 socket 数量、
端口预测目标、撒网范围全都依赖对端信息，而这些信息要到候选已经定型之后才拿得到。

#### 2. 向 100 个候选每 10ms 狂发包，把自己的端口计数器推乱了

2.x 的打洞是"一刀切扫射"：把拿到的所有候选（往往上百个，包含对端全部内网地址）
统统塞进一个循环，每 10ms 全量发一轮。

对锥形 NAT 来说这只是浪费。但对**线性对称 NAT** 来说这是自伤：
这类 NAT 的出口端口是一个**递增计数器**，每向一个新目标发包就前进一格。
向 100 个候选发一轮，等于把自己的计数器一次推进 100 格——
对端刚刚基于 STUN 采样算出来的端口预测值，在它发出第一个包之前就已经作废了。

**这与网络拥塞完全无关，候选越多、发得越勤，破坏越彻底。**

#### 3. 中继槽位每个房间都预分配，且从不回收

2.x 给每个房间预先分配中继资源，房间存在期间一直占着，
即使房间里所有人早就打洞成功走了直连也不释放。
结果是**中继资源消耗量等于房间总数，而不是打洞失败数**——
打洞做得再好，中继压力也一点不减。

以上三条决定了 3.0 必须重做协议流程、重做打洞引擎、重做服务端资源模型。

### 一、协议层：破坏性变更

`crates/protocol` 是客户端与服务端共享的信令协议（MessagePack 序列化）。

#### `PROTOCOL_VERSION = 2`，不做向后兼容

客户端在鉴权时上报协议版本，**版本不符直接拒绝连接**并返回提示：

```
客户端版本过旧，请升级后再使用
```

不做兼容层是有意的：3.0 的打洞流程是三阶段握手，2.x 是单阶段候选交换，
两者不存在"降级共存"的中间态。留一条兼容路径只会让两套逻辑互相掩盖 bug。

> **部署 3.0 服务端 = 所有客户端必须同步升级。**

#### 打洞改为三阶段握手

```text
阶段一   客户端 NatProfileReport  ──►  服务端凑齐房间内双方画像
阶段二   服务端 PunchPlan          ──►  下发策略 + 角色 + 参数
阶段三   服务端 PunchStart         ──►  统一起始时刻，双方定向打洞
                                        ──►  PunchReport（遥测回传）
```

关键点是**候选生成推迟到收到 `PunchPlan` 之后**。
客户端拿到策略才知道要开几个 socket、打哪些端口，这才让"按 NAT 组合选策略"真正成立。

#### `PunchStrategy::select()` 是策略矩阵的唯一真相源

策略选择函数定义在共享的 protocol crate 里，**服务端与客户端调用同一份代码**：

```rust
pub fn select(
    local: NatClass,
    remote: NatClass,
    ipv6_both: bool,
    same_public_ip: bool,
) -> PunchStrategy
```

有单元测试保证：对任意 NAT 组合，从 A 视角和从 B 视角推导出的策略互为**镜像角色**
（一侧是 `ConeToLinear`，另一侧必然是 `LinearToCone`）。

两侧角色错配是打洞失败最隐蔽的一类原因——比如双方都以为自己该撒网，
于是两个对称 NAT 同时把彼此的端口预测推乱。这类 bug 靠日志几乎查不出来，只能用共享代码和测试约束住。

#### Ping/Pong 带时间戳，打洞起始时刻自适应

打洞要求双方**同时**开始发包。2.x 的做法是服务端定一个"200ms 之后开始"的固定提前量。

这个数字在同城链路上偏大，在跨省 / 跨运营商链路上则完全不够——
信令 RTT 本身就超过 200ms 时，`PunchStart` 到达客户端时约定的时刻**早已过期**，
两侧实际错开几百毫秒各打各的，NAT 映射根本对不上。

3.0 让 Ping/Pong 携带时间戳，服务端持续测量到每个客户端的信令 RTT，
按实测值计算起始时刻，保证双方**真的**在同一时间窗口内发包。

#### `PunchRecord` 遥测

成功和失败都上报，包含双方 NAT 分类、选中的策略、结果类型：

| `PunchOutcome` | 含义 |
|---|---|
| `P2pSuccess` | P2P 直连成功 |
| `PunchTimeout` | 打洞窗口超时 |
| `FirewallBlocked` | 检测到防火墙阻断，主动放弃 |
| `NoSrflx` | STUN 探测失败，拿不到公网映射候选 |
| `StrategyUnsupported` | 策略判定为不可打洞 |
| `RelayFallback` | 已回退到中继 |

只统计成功率是不够的——**失败必须带原因**，否则无法区分"NAT 组合本身难打"
和"我们的策略实现有问题"。

### 二、打洞引擎：四条原则与 8 种策略

新引擎在 `crates/core/src/punch.rs`。它的核心不是"更努力地发包"，而是四条原则。
**这四条都固化成了代码约束，不是注释里的建议。**

#### NAT 三分类

| 分类 | 含义 |
|---|---|
| `Cone` | 锥形——出口端口固定，对不同目标复用同一映射 |
| `LinearSymmetric` | 线性对称——端口按固定步长递增，**可预测** |
| `RandomSymmetric` | 随机对称——端口随机分配，只能撒网 |
| `Unknown` | 探测失败，按最保守的锥形处理再试一次 |

**只分三类是有意的**：打洞策略只关心"端口能不能预测"。
锥形 NAT 内部的 NAT1/2/3 子类在打洞行为上没有区别，细分不带来收益，只会让矩阵膨胀。

步长判定用**众数而非平均值**——平均值会被个别异常步进（其他应用抢占端口）带偏。
判定还要求正向小步进（1~16）在全部采样中占比不低于 60%，否则直接判为随机。

#### 原则 A：可预测的一侧必须"安静"

线性对称 NAT 每向一个**新目标**发包，出口端口计数器就前进一格，
对端刚算出的预测值会立刻作废（就是重写起因第 2 条）。

落地为 `PunchParams::quiet`：为真时**只允许向策略指定的目标发包**，一个都不能多。

#### 原则 B：撒网成本严重不对称

- 锥形 NAT 撒 K 个目标：**1 个 socket 发 K 个包**（映射固定，可复用）
- 对称 NAT 撒 K 个目标：**需要 K 个 socket**（每个目标一个新映射）

所以**撒网必须由锥形侧承担**，对称侧只负责用最少的 socket 稳定打固定目标。
角色分工由服务端下发，两侧不能对称地执行同一套逻辑。

#### 原则 C：撒网只是"开门"，triggered check 才是主路径

向猜测地址发包的真正目的**不是命中**，而是在本端 NAT 上打开对这些地址的**入向过滤**。

一旦对端的包能进来，就能从数据报源地址读到它的真实 `IP:port`（prflx 候选），
立即定向回包即可建立双向通道。所以**猜错端口不要紧**——
但 prflx 的处理必须走快路径：收到未知源地址的包要立刻密集回包（5 次 × 10ms 间隔），
不能等下一轮定时器。

#### 原则 D：不可达候选首次失败就淘汰

向对端内网地址（`192.168.*` 之类）发包会得到 `ENETUNREACH`——本机压根没有到那些网段的路由。
这类错误是**永久性**的，重试一万次结果一样。

2.x 会每 20ms 重试一次直到 12 秒窗口结束，白白吃掉发包预算。
3.0 **首次 `ENETUNREACH` 即摘除**该候选。

#### 8 种策略矩阵

按 `(本端 NAT, 对端 NAT)` 组合选择，外加两条快速通道：

| 策略 | 组合 | 做法 |
|---|---|---|
| `DirectIpv6` | 双方都有 IPv6 | 快速通道：无 NAT，只需打开双方状态防火墙 |
| `DirectLan` | 公网 IP 相同 | 快速通道：同一出口，直接走内网地址 |
| `ConeToCone` | 锥形 ↔ 锥形 | 双方端口都固定且已知，最简单 |
| `ConeToLinear` | 锥形 → 线性 | 本端按步进**预测**对端端口 |
| `LinearToCone` | 线性 → 锥形 | 本端**必须安静**，只打对端固定端口 |
| `ConeToRandom` | 锥形 → 随机 | 本端向对端**大范围撒网**（1 socket 多目标） |
| `RandomToCone` | 随机 → 锥形 | 本端开 **N 个 socket** 打对端固定端口 |
| `BothLinear` | 线性 ↔ 线性 | 双方各自预测对方，**双方都必须安静** |
| `LinearToRandom` | 线性 → 随机 | 本端少量 socket 撒网，需控制端口漂移 |
| `RandomToLinear` | 随机 → 线性 | 本端开 N 个 socket 打对端**预测**端口 |
| `BothRandom` | 随机 ↔ 随机 | 生日悖论双向撒网，成本最高 |
| `RelayOnly` | —— | 判定不可打洞，直接走中继 |

IPv6 直连的候选优先级高于所有 IPv4 候选——IPv6 通常不经过 NAT，直连成功率接近 100%。
任一侧 NAT 探测失败（`Unknown`）时退回 `ConeToCone`，试一次的成本远低于直接放弃。

#### 收发路径的工程修正

这些不涉及策略，但直接决定上面的策略能不能真的跑起来：

- **接收循环 drain 到 `WouldBlock`**：一次唤醒把 socket 缓冲里的包全部读干净，
  而不是读一个就回去等下一轮。打洞窗口里包是成簇到达的，一次读一个必然积压。
- **放大 `SO_RCVBUF`**：撒网阶段瞬时包量很大，默认缓冲区会静默丢包，
  丢掉的恰恰可能是唯一那个带正确 prflx 地址的包。
- **Windows 关闭 `SIO_UDP_CONNRESET`**：不关的话，一个 ICMP 端口不可达错误
  会让后续 `recv_from` 直接返回错误，**堵死整条接收路径**。
  打洞过程中收到 ICMP 不可达是家常便饭（对端 NAT 还没开门），
  这个 Windows 特有行为会让打洞在第一个 ICMP 到达时就静默死掉。

### 三、数据面：QUIC DATAGRAM 与 overlay 端到端加密

#### 从可靠有序流改为 DATAGRAM（RFC 9221）

2.x 用 QUIC 的可靠有序流承载隧道流量。**这对三层隧道是错的**：

1. **队头阻塞**——一个包丢了，后面所有已经到达的包都得排队等重传，
   而三层隧道里这些包往往属于完全不相干的连接；
2. **重传早已过期的实时包**——游戏状态、语音这类数据迟到等于无用，
   QUIC 还在忠实地重传它们，白占带宽；
3. **重传叠加**——内层 TCP 有自己的重传定时器，外层 QUIC 也在重传，
   两层互相误判，吞吐量直接崩塌。

隧道要的是 **IP 语义**：尽力而为、不保序、不重传，可靠性由上层协议自己负责。
3.0 全面改用 QUIC DATAGRAM。

顺带的简化：`send_datagram` 是**同步非阻塞**的（要么立刻入队，要么立刻失败），
所以 2.x 那套"每个对端一条发送队列 + 写超时 + 队列积压处理"的机制**整个删掉了**。

#### Overlay 端到端加密：X25519 + ChaCha20-Poly1305

**为什么 QUIC 自带加密还要再加一层：**

数据面统一走 DATAGRAM 之后，**中继模式下的 QUIC 是逐跳的**——
Guest ↔ 中继是一条连接，中继 ↔ Host 是另一条连接。
中继站在中间，**能看到完整明文**。

所以真正的机密性必须由 overlay 自己提供，让中继退化成一个**盲转发器**。

P2P 直连时这一层确实是冗余的（QUIC 本就加密），但保持两条路径数据面一致比省下这点开销更重要——
否则中继与直连要维护两套收发逻辑，bug 会互相掩盖。

**为什么临时密钥必须签名：**

```text
A: eph_pub_a, sign(id_a, eph_pub_a)  ──信令──►  B 验签
B: eph_pub_b, sign(id_b, eph_pub_b)  ──信令──►  A 验签
双方: shared = X25519(eph_priv, eph_pub_peer)
      HKDF-SHA256(shared, salt=session_salt) → 两个方向各一把密钥
```

临时 X25519 公钥通过信令交换，而**信令服务器同时也是中继运营方**。
不签名的话，它可以在转发时替换双方的公钥、与两边各自握手，完成一次完美的中间人攻击——
而 overlay 加密的全部意义就是防这个。用长期 Ed25519 身份密钥签名才能封死这条路。

报文格式：

```text
[ 8 字节大端计数器 ][ ChaCha20-Poly1305 密文 + 16 字节 tag ]
```

计数器同时充当 nonce 与重放检测序号。**同一把密钥下 nonce 绝不能重复**，
因此收发方向使用两把独立派生的密钥，各自维护自己的计数器。
重放窗口 2048 个包——乱序是 DATAGRAM 的常态，窗口太窄会误杀正常流量。

#### TUN MTU = 1160

```rust
pub const TUN_MTU: u16 = 1160;
```

这个值不是随手定的：要保证一个满载的内层 IP 包，加上 overlay 加密开销（8 字节计数器 + 16 字节 tag）
和 QUIC / UDP / IP 各层头部之后，**仍然能塞进一个 QUIC 数据报**。
DATAGRAM 是不分片的——超出就是丢弃，而且是静默丢弃。

### 四、服务端：自建 STUN 与单端口中继

#### 自建 STUN，双端口

**为什么必须自建：**

STUN 是打洞链路上**唯一不可绕过**的一环。拿不到 srflx 候选（公网映射）
就不知道自己的出口地址，端口预测和撒网都无从谈起，只能落中继。

实测中曾出现三台境外公共 STUN 服务器在**同一次会话内全部超时**的情况——
等于打洞还没开始就已经失败。把这么关键的依赖交给不可控的第三方是不合理的。

**为什么必须两个端口（`3478` + `3479`）：**

这不是冗余备份。**判定 NAT 映射行为至少需要两个不同的目标端点**：
客户端用同一个源 socket 分别打这两个端口，比较返回的映射端口是否一致——
一致是锥形，不一致是对称。只有单个端点时，NAT 分类只能靠猜。

> **两个端口都必须在防火墙放行，缺一个就无法判定 NAT 类型。**

#### `NetworkConfig` 由服务端下发

客户端**不内置任何服务器地址与端口常量**。鉴权成功后服务端下发：

```rust
pub struct NetworkConfig {
    pub stun_servers: Vec<StunServerInfo>,  // 按优先级排序，自建在前
    pub relay_addr: String,
    pub relay_quic_port: u16,
}
```

这样自建部署者改一次 `config.toml` 就够了，不需要重新编译客户端。

#### 中继收敛成单端口（默认 443/UDP）

2.x 是"每个房间一个中继端口"。3.0 改成**全局唯一端口，所有房间共用**。

理由：**房间路由本来就靠 QUIC 首流里的 token，监听端口从不参与识别**。
既然端口不承载任何信息，"每房间一个端口"就是一个纯冗余的维度——
它唯一的实际效果是把并发上限锁死在端口数量上，
而真实瓶颈是**带宽**（按每房间双向 5 Mbps 估算，100 个并发就已接近 1 Gbps）。

默认选 **443/UDP** 的理由：企业、校园、酒店等受限网络普遍放行这个端口（QUIC / HTTP3 就跑在上面），
而中继连不上就意味着彻底失败，所以这里的穿透率很关键。
注意 **TCP/443 与 UDP/443 是两套独立的端口空间**，不会和你的 HTTPS 服务冲突。

#### 中继槽位回收

房间内**全员上报已切换到 P2P 直连**后，服务端释放该房间的中继 token 与槽位。
这样中继消耗量才真正等于**打洞失败数**，而不是房间总数（重写起因第 3 条）。

#### 打洞遥测聚合

客户端上报的 `PunchRecord` 在服务端聚合成 **NAT 组合成功率矩阵**：

```
GET /api/punch/stats
```

这是判断"某个策略实现是否有效"的唯一客观依据。
只读管理面板（默认关闭）还提供 `/api/login` 与 `/api/sessions`。

### 五、观测体系

前提：**观测模型是集中式的**。用户不会主动收集日志，所以排障靠客户端把整个 `log/` 目录打包上传。
这决定了本地日志的要求是**可被机器消费**，而不是给人看。

#### 日志按用途分文件

实测单次 8 小时会话产出 48,736 行 / 6 MB，其中 **91.4% 是 DEBUG**，
且绝大多数是每秒一条、数值完全相同的心跳（带宽采样、`get_stats`、QUIC path 统计）。
真正有价值的打洞过程被彻底淹没。

拆分规则按**用途**而非级别：

| 文件 | 内容 | 级别 |
|---|---|---|
| `ice.log` | 打洞全过程（核心，值得全量记） | DEBUG |
| `signal.log` | 信令连接、鉴权、房间、消息收发 | INFO |
| `tunnel.log` | 隧道、TUN、数据面 | INFO |
| `app.log` | 其余一切 | INFO |

- **按大小轮转**（单文件 8 MB，保留 5 份），旧文件移入 `archive/` 子目录。
  用大小而非时间：我们要控的是**上报体积**。按时间轮转在空闲时产生一堆空文件，
  在繁忙时又可能让单文件涨到几百 MB。
- **模板去重**：同一模板在 10 秒窗口内重复出现时只保留首末两条，中间折叠为计数。
  这是把 6 MB 压到可上报体积的关键。
- 高频心跳指标**不进文本日志**——它们属于结构化指标，走 `PunchRecord` 那条路。

#### 完整日志包上传

- **zip 打包**整个 `log/`（含 `archive/`），单包上限 32 MB。
  用 zip 而非自定义格式，是为了管理员拿到后能直接解压查看——排障时多一道解包工具就是多一道障碍。
- 走**独立 HTTP POST**（默认 `:10211`）而不是信令 WebSocket：
  日志包可能几 MB，塞进信令连接会阻塞打洞协商这类时延敏感的消息。
- **一次性凭据**授权上传。
- **失败重投队列**：上传失败（断网、服务端重启）时把包留在本地 `pending/`，下次连接成功后补投。
  否则恰恰是"网络有问题"的那一次日志——最有排障价值的那份——最容易丢。
- **每日配额**（64 MB）：日志上报本身不能变成流量负担，尤其在用户网络已经不好的时候。
- 触发方式两种：用户主动"反馈问题"，或服务端针对特定 `user_id` 主动索取。

### 六、删除的东西

| 删除项 | 原因 |
|---|---|
| `server/src/port_pool.rs` | 中继收敛成单端口后，端口池这个概念整个消失了 |
| 裸 UDP 中继路径 | 编译器证实：这条路径除了它自己的单元测试之外**从未被任何代码调用过** |
| 每对端发送队列 + 写超时 | `send_datagram` 同步非阻塞，这套机制失去了存在意义 |

```text
│   管理面板       :10210   ── 只读，默认关闭                     │
└──────────────────────────────────────────────────────────────┘
             ▲                                    ▲
             │  信令 (MessagePack over WebSocket) │
             ▼                                    ▼
   ┌───────────────────┐                ┌───────────────────┐
   │   Host 客户端      │  ◄── P2P ──►   │   Guest 客户端     │
   │                   │   （打洞成功）  │                   │
   │  TUN 虚拟网卡      │                │  TUN 虚拟网卡      │
   │  MTU 1160         │  ◄── 中继 ──►  │  MTU 1160         │
   │                   │   （打洞失败）  │                   │
   └───────────────────┘                └───────────────────┘
       overlay 端到端加密：X25519 + ChaCha20-Poly1305（两条路径都加）
```

### Crate 划分

| Crate / 目录 | 职责 |
|---|---|
| `crates/protocol` | 客户端与服务端**共享**的信令协议：消息定义、`NatClass`、`PunchStrategy::select()` 策略矩阵、`PunchRecord` 遥测。MessagePack 序列化。 |
| `crates/core` | 平台无关引擎：NAT 探测、打洞、STUN 客户端、QUIC 隧道、TUN 网卡、信令客户端、overlay 加密、日志与上报。 |
| `src-tauri` | 桌面客户端（Tauri 后端），前端在 `src/`。 |
| `src-web` | Linux headless 客户端，自带 WebUI。 |
| `server` | 信令 + 中继 + 自建 STUN + 日志接收 + 管理面板。 |
| `crates/mobile` + `android/` | 安卓端。**3.0 未适配，暂不可用。** |
| `crates/macos-helper` | macOS 上负责 TUN 网卡创建的特权 sidecar。 |

## 快速开始

### 一、部署服务端

需要一台**有公网 IP** 的服务器。

```bash
# 1. 拿到 phantom-server 二进制（见「构建说明」，或从 GitHub Actions 产物下载）
#    首次运行会在当前目录自动生成默认 config.toml
./phantom-server

# 2. 编辑 config.toml（见下方「必须修改的配置」）

# 3. 指定配置文件启动
./phantom-server --config /path/to/config.toml
```

配置文件查找顺序：`--config <path>` → 当前目录 `config.toml` → 可执行文件同目录 → `server/config.toml`。
全部找不到时使用默认值并生成一份配置文件。

#### 必须修改的配置

```toml
[relay]
public_addr = "127.0.0.1"   # ← 必须改成真实公网 IP 或域名
quic_port   = 443           # 全局单端口，注意防火墙放行 UDP/443

[stun]
enabled  = true
port     = 3478
alt_port = 3479             # ← 两个端口都要放行，缺一个就无法判定 NAT 类型

[log_upload]
public_base = ""            # 留空则按 http://<relay.public_addr>:10211 推导
```

> ⚠️ **最常见的部署错误**：`relay.public_addr` 忘了改，还是 `127.0.0.1`。
> STUN 对外公布地址和日志上传基址都默认从它推导，
> 结果是客户端拿到 `127.0.0.1`，**STUN 与日志上传全部不可用**，
> 表现为所有房间都落中继、且无法远程排障。

#### 防火墙放行清单

| 端口 | 协议 | 用途 | 必需 |
|---|---|---|---|
| 10209 | TCP | 信令 WebSocket | 是 |
| 443 | **UDP** | 中继 QUIC（与 TCP/443 互不影响） | 是 |
| 3478 | UDP | STUN 主端口 | 是 |
| 3479 | UDP | STUN 备用端口（NAT 判定必需） | 是 |
| 10211 | TCP | 日志包上传 | 建议 |
| 10210 | TCP | 管理面板 | 默认仅本机 |

### 二、使用客户端

#### 桌面端（Windows / macOS / Linux）

1. 下载对应平台的安装包并安装；
2. 启动后在设置里填入你的信令服务器地址；
3. 一台设备**创建房间**（成为 Host），其余设备**加入房间**（成为 Guest）；
4. 创建 TUN 网卡需要特权：
   - Windows：以管理员身份运行；
   - macOS：由特权 sidecar `phantom-macos-helper` 负责，首次会请求授权；
   - Linux：需要 root 或 `CAP_NET_ADMIN`。

#### Linux headless 客户端

```bash
sudo ./phantom-p2p [选项]
```

| 参数 | 默认值 | 说明 |
|---|---|---|
| `--bind <ADDR>` | `0.0.0.0:9080` | 本地管理 WebUI 监听地址（同一端口也会在 Host 虚拟 IP 上打开） |
| `--signal <URL>` | 内置官方端点 | 信令服务器 WebSocket 地址 |
| `--no-auto-room` | 关闭 | 鉴权后**不**自动创建 Host 房间 |
| `-v`, `--verbose` | 关闭 | 输出 DEBUG 级日志 |

启动后浏览器访问 `http://<主机>:9080` 进行操作。Linux TUN 需要 root 或 `CAP_NET_ADMIN`。

## 配置说明

`server/config.toml` 完整字段：

### `[signal]` — 信令服务

| 字段 | 默认 | 说明 |
|---|---|---|
| `bind` | `0.0.0.0` | 信令 WebSocket 监听地址 |
| `port` | `10209` | 信令端口 |

### `[relay]` — 中继

| 字段 | 默认 | 说明 |
|---|---|---|
| `public_addr` | `127.0.0.1` | **必改**。下发给客户端的公网 IP / 域名；STUN 与日志上传地址也默认从它推导 |
| `quic_port` | `443` | 全局唯一中继 QUIC 端口，所有房间共用 |
| `token_ttl_secs` | `120` | 中继 token 过期时间（秒） |

### `[stun]` — 自建 STUN

| 字段 | 默认 | 说明 |
|---|---|---|
| `enabled` | `true` | **强烈建议保持开启**，关闭后 NAT 探测只能依赖公共服务器 |
| `port` | `3478` | 主端口 |
| `alt_port` | `3479` | 备用端点，**NAT 映射行为判定必需，不是冗余** |
| `public_addr` | `""` | 对外公布的 STUN 地址，留空复用 `relay.public_addr` |
| `fallback_servers` | `[]` | 第三方公共 STUN 兜底，格式 `["host:port", ...]` |

### `[log_upload]` — 日志接收

| 字段 | 默认 | 说明 |
|---|---|---|
| `enabled` | `true` | 关掉就没法远程排障了 |
| `bind` | `0.0.0.0:10211` | 接收服务监听地址 |
| `public_base` | `""` | 下发给客户端的可访问基址（含协议与端口），留空按 `http://<relay.public_addr>:<bind 端口>` 推导 |
| `store_dir` | `log_uploads` | 落盘目录，按 `user_id` 分子目录存放 |

### `[port_allocation]` — Guest 本地端口池

| 字段 | 默认 | 说明 |
|---|---|---|
| `guest_port_start` | `25600` | 本地端口池起始 |
| `guest_port_end` | `25700` | 本地端口池结束 |

### `[auth]` — 鉴权

| 字段 | 默认 | 说明 |
|---|---|---|
| `enabled` | `true` | Ed25519 鉴权。关闭后所有客户端直接通过 |

### `[admin]` — 管理面板

| 字段 | 默认 | 说明 |
|---|---|---|
| `enabled` | `false` | 只读管理面板，需自建者显式开启 |
| `bind` | `127.0.0.1:10210` | 默认仅本机可访问。改为 `0.0.0.0:10210` 意味着你自行承担相应的安全防护责任 |

管理面板接口：`POST /api/login`、`GET /api/sessions`、`GET /api/punch/stats`。

## 构建说明

### 正式构建必须走 GitHub Actions

本项目**无法在本地做交叉编译**（Tauri 打包、各平台原生依赖、NSIS、macOS sidecar 等）。
正式产物一律通过 `.github/workflows/build.yml` 产出。

触发方式：推送到 `main`、提 PR，或手动 `workflow_dispatch`（可选择单个平台或 `all`）。

支持的目标平台：

## 已知限制

### 安卓端 3.0 未适配，暂不可用

`crates/mobile` 与 `android/` 尚未跟进 3.0 的协议变更。
由于 `PROTOCOL_VERSION` 提到 2 且**不做向后兼容**，
现有安卓客户端连接 3.0 服务端会被直接拒绝（提示"客户端版本过旧，请升级后再使用"）。
**适配完成前请勿使用安卓端。**

### 其它限制

- **协议不向后兼容**：升级服务端到 3.0 时，所有客户端必须同步升级，没有灰度路径。
- **本地无法交叉编译**：正式产物只能通过 GitHub Actions 产出，本地仅能 `cargo check` / `cargo test`。
- **需要特权**：创建 TUN 网卡在所有平台都需要管理员 / root / `CAP_NET_ADMIN`。
- **必须有公网服务器**：信令、中继、STUN 都需要一个有公网 IP 的部署点。
- **中继带宽是硬瓶颈**：单端口模型下并发上限由带宽决定（按每房间双向 5 Mbps 估算，
  100 个并发接近 1 Gbps）。打洞成功率直接决定中继压力。
- **NAT 探测失败时按锥形处理**：拿不到足够 STUN 采样时会乐观地按 `Cone` 试一次。
  试一次的成本远低于直接放弃，但成功率无保证。
- **管理面板默认关闭**且仅监听本机。若改为对外监听，安全防护由部署者自行负责。
